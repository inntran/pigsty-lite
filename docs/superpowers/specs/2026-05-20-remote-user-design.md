# Configurable Ansible remote user — design

Date: 2026-05-20

## Problem

`ansible.cfg` sets `become = True` / `become_ask_pass = False` but never sets a
`remote_user`. Ansible therefore connects to every target host as whatever OS
user invoked the playbook on the control node. There is no way to choose the
login user, and nothing tells the operator what that user must be able to do.

We want:

1. A configurable remote login user, defaulting to `dba`, overridable during the
   `configure` step.
2. A clear, hard-to-miss statement of the connection contract: the remote user
   must have **passwordless SSH (key auth)** and **NOPASSWD sudo** on every
   target host. Setting that up is the operator's responsibility — pigsty-lite
   documents the expectation, it does not configure or verify it.

## Non-goals

- No connectivity / SSH / sudo preflight check. If the contract is not met, the
  first `make plan` fails naturally with an Ansible connection or `become`
  error; that feedback is sufficient.
- No management of SSH keys or `sudoers` files on target hosts.
- No change to `become` behavior — `become = True`, `become_method = sudo`,
  `become_ask_pass = False` are already correct.

## Naming note

The response file already has a `db_routing` section (HAProxy / VIP
manager). To avoid confusion with that unrelated section, the new section is
named **`access`**, not `connection`.

## Design

### 1. Response file — new optional `access` section

```yaml
access:
  # Ansible logs in as this user on every target host. It must have
  # passwordless SSH (key auth) and NOPASSWD sudo. pigsty-lite does not
  # configure this — set it up yourself. See docs/operations/firstrun.md.
  ansible_user: dba
```

The whole `access` section is **optional**, consistent with how `network` is
optional. Absent → `ansible_user` defaults to `dba`.

### 2. Schema — `bin/_response_schema.py`

New validator `_validate_access(value) -> str`:

- `value is None` → return `"dba"`.
- Not a mapping → `SchemaError("access: must be a mapping")`.
- `ansible_user` defaults to `"dba"` when absent.
- `ansible_user` must be a non-empty string, else `SchemaError`.
- Returns the resolved `ansible_user`.

Wired into `validate()` next to `_validate_network`:
`_validate_access(data.get("access"))`.

### 3. Generator — `bin/_generate_response_vars.py`

Emit one new key into `group_vars/response.yml`:

```yaml
ansible_user: dba
```

Resolved as `response.get("access", {}).get("ansible_user", "dba")`. Placed
near the top of the `out` dict with the other cluster-level keys.

`_generate_inventory.py` is unchanged — `ansible_user` is a group var, not part
of the host/group inventory structure.

### 4. `ansible.cfg`

No `remote_user` line. The value flows entirely through
`group_vars/response.yml` (`ansible_user`), so it stays tied to the response
file as the single source of truth and is regenerated by `make regen`.

### 5. Interactive wizard — `configure`

Add a 4th prompt after `cluster_domain`:

```
Remote user [dba]:
```

Sets `data["access"]["ansible_user"]`. The wizard still writes only
`responses/site.rsp.yml`.

The closing message gains a clearly set-off block stating the connection
contract — printed every interactive run so it is hard to miss:

```
+--------------------------------------------------------------+
|  BEFORE you run `make plan` / `make deploy`:                  |
|                                                              |
|  The remote user '<ansible_user>' must already have, on      |
|  EVERY target host:                                          |
|    1. Passwordless SSH login (SSH key authentication)        |
|    2. NOPASSWD sudo                                          |
|                                                              |
|  pigsty-lite does not set this up. make plan will fail with  |
|  a connection or sudo error if it is not in place.           |
+--------------------------------------------------------------+
```

`<ansible_user>` is interpolated with the chosen value.

### 6. Example response files

Add the `access` block (with the explanatory comment) to both
`responses/ha.rsp.yml.example` and `responses/spof.rsp.yml.example`, so files
copied directly per `firstrun.md` are complete and self-documenting.

### 7. Docs — `docs/operations/firstrun.md`

Expand the Prerequisites bullet "SSH access from the control node with `become`
privileges" into an explicit requirement: the `access.ansible_user` (default
`dba`) must have passwordless SSH key auth and NOPASSWD sudo on every target
host, with an example `/etc/sudoers.d` snippet, e.g.:

```
# /etc/sudoers.d/dba
dba ALL=(ALL) NOPASSWD: ALL
```

## Testing

- **Schema** (`tests/configure/test_schema.py`): `access` absent → valid;
  `access.ansible_user` custom value → valid; `access` not a mapping → rejected;
  `ansible_user` empty string / non-string → rejected.
- **Generator** (`tests/configure/test_generate_response_vars.py` or
  equivalent): `ansible_user` key present in output; defaults to `dba` when
  `access` absent; reflects a custom value.
- **Wizard** (`tests/configure/test_configure_cli.py`): the 4th prompt sets
  `access.ansible_user` in the written response file; default `dba` applied on
  empty input.

## Files touched

- `bin/_response_schema.py` — new `_validate_access`, wired into `validate()`.
- `bin/_generate_response_vars.py` — emit `ansible_user`.
- `configure` — 4th wizard prompt + connection-contract block in closing output.
- `responses/ha.rsp.yml.example`, `responses/spof.rsp.yml.example` — `access` block.
- `docs/operations/firstrun.md` — expanded prerequisite + sudoers example.
- `tests/configure/` — schema, generator, wizard tests.
