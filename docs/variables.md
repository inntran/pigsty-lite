# Variables in pigsty-lite

This is a map of where variables live, who owns them, and how they override
each other. It does not list every variable — for that, read the source
files referenced below.

## Precedence (low → high)

Ansible evaluates many layers; pigsty-lite uses only the ones below. Later
layers win.

| # | Layer | Location | Purpose |
|---|---|---|---|
| 1 | Role defaults | `roles/<role>/defaults/main.yml` | Role-local concerns. Safe values when the role runs in isolation. |
| 2 | `group_vars/all` | `group_vars/all/main.yml` | Cluster-wide constants every host needs: ports, paths, versions, identity. |
| 3 | `group_vars/<group>` | `group_vars/postgres.yml`, `etcd.yml`, `monitor.yml`, `backup_server.yml` | Per-group contract — values that cross role boundaries within one group. |
| 4 | Inventory host vars | `inventory/<profile>.yml` (per host) | Identity per machine: `ansible_host`, `postgres_role`, `etcd_seq`. |
| 5 | `group_vars/response.yml` | Generated by `./configure -s -f responses/site.rsp.yml` | Operator-facing overrides for a real deployment. **Do not edit by hand.** |
| 6 | `--extra-vars` | CLI | Last-resort one-off. Avoid in normal flows. |

Higher layers also win inside molecule scenarios via `provisioner.inventory.group_vars`
(layer 2/3 equivalent), `host_vars` (layer 4), and `set_fact` in prepare/converge
plays (effectively layer 6, since set_fact wins over everything else).

## What lives where, and why

### Role defaults — `roles/<role>/defaults/main.yml`

Hold values that are **local to the role's task list**. If you ran the role
in isolation against a fresh host, these defaults should make it work without
any group_vars at all — except where the role explicitly declares a contract
with another role (see below).

Examples that belong here:

- Package names (`postgres_pkg_server`).
- Filesystem modes the role's own tasks `chmod` to (`postgres_data_dir_mode`).
- Systemd unit names the role manages (`postgres_vendor_systemd_unit`).
- Role-prefixed knobs that no other role reads (`etcd_election_timeout`).

Examples that do **not** belong here:

- Anything two roles both consume — that's a contract; promote to group_vars.
- Anything an operator is expected to set per cluster — that belongs in the
  response file, surfaced via `group_vars/response.yml`.

### `group_vars/all/main.yml` — cluster-wide constants

The file every host loads. Use it for values where there is exactly one
correct answer for the whole cluster:

- Identity: `cluster_name`, `cluster_domain`.
- Network shape: `network_loopback_addresses`, `network_any_address`.
- Ports: `postgres_port`, `pgbouncer_port`, `haproxy_*_port`, `patroni_rest_port`, etc.
  Ports live here (not in role defaults) because multiple roles on multiple
  hosts must agree on them — haproxy on the monitor host needs the same
  `postgres_port` value the postgres role uses.
- Versions: `postgres_version`.
- Paths shared across roles: `pigsty_pki_dir`, `etcd_data_dir`, `backup_server_path`.
- Repo policy, cert validity, backup conventions, monitoring host pointer.

If only one role reads it and there's no cross-role coordination, it does
not belong here — push it back into the role's defaults.

### `group_vars/<group>.yml` — per-group contract

These files exist to encode **decisions shared between roles that both run
on hosts in that group**.

- `group_vars/postgres.yml` is the busiest: it owns the contract between
  the `postgres` role (install + filesystem) and the `patroni` role
  (configuration + cluster). Both consume `postgres_user`, `postgres_group`,
  `postgres_data_dir`, `postgres_listen_address`, etc. The patroni role's
  defaults declare these as hard reads (no `default()` fallback) — a
  missing value here is a setup error, not something to paper over.
- `group_vars/etcd.yml` carries `etcd_initial_cluster_state` because that
  value differs between bootstrap and ongoing operation, and only operators
  flip it.
- `group_vars/monitor.yml` and `group_vars/backup_server.yml` are empty
  by design — the role defaults already cover everything, and the files
  exist as documented override points for operators who split those
  responsibilities onto dedicated hosts.

The header comments in each `group_vars/*.yml` state the same. Add a comment
when you add a variable so the next reader knows why it isn't a role default.

### Inventory host vars — `inventory/<profile>.yml`

Identity, not configuration. Each host gets:
- `ansible_host` — its real IP. Used everywhere as the canonical address.
- `postgres_role` — `primary` or `replica`. The patroni role's `_assert.yml`
  fails the play if exactly one primary isn't declared.
- `postgres_seq`, `etcd_seq` — stable ordinals for log/identifier naming.

Do not put cluster-wide config here. If you find yourself copying the same
value into every host, promote it to `group_vars/all` or `group_vars/<group>`.

### `group_vars/response.yml` — operator-facing layer

Generated by `./configure -s -f responses/site.rsp.yml`. The response file
is the **only** place an operator should be editing for production. The
generator (`bin/_generate_response_vars.py`) translates the human-friendly
response schema into Ansible variables and writes them into
`group_vars/response.yml` with a `# GENERATED FILE` banner.

This layer overrides everything below it. That's how operators tune
passwords, CIDRs, backup schedules, and tuning profiles without touching
the repo.

### Why the contract has no `default()`

Earlier code had chains like
`patroni_postgres_listen_address: "{{ postgres_listen_address | default(network_any_address | default('0.0.0.0')) }}"`.
That looked safe but masked a real bug: if `group_vars/postgres.yml` wasn't
loaded (e.g., a misconfigured molecule scenario), Patroni silently fell
back to `0.0.0.0` and the cluster appeared to work — until something else
depended on the configured listen address.

The rule now: **role defaults that consume a group_vars contract use hard
reads**. `roles/patroni/defaults/main.yml` reads `postgres_user`,
`postgres_data_dir`, etc., with no `default()`. A missing value crashes
the play with `'postgres_user' is undefined`, which points immediately at
the real problem (missing group_vars).

The same logic applies to passwords: `vault_*` overrides exist (`patroni_superuser_password: "{{ vault_patroni_superuser_password | default('postgres-dev-password-change-me') }}"`)
but the dev fallback is a literal change-me string, so a forgotten vault
override is visible in the rendered config.

## Adding a new variable — decision flow

1. **Only one role reads it?** → role defaults.
2. **Multiple roles read it, but they all run on hosts in one group?**
   → `group_vars/<group>.yml`. Document in the file header.
3. **Multiple roles, multiple groups?** → `group_vars/all/main.yml`. Group
   it under the matching section header (Ports, Paths, etc.).
4. **Operator-tunable in production?** → add to the response schema and
   the generator; do not require operators to touch `group_vars/` directly.
5. **Per-host?** → inventory host vars, and only if it's identity (sequence
   number, role, address). Not configuration.

## Variables in tests (molecule scenarios)

Molecule scenarios run from `tests/molecule/<role>/molecule/<scenario>/`
and have their own variable surface. The repo-root `group_vars/` files
**are** loaded by molecule (because the scenario's generated inventory
sits inside a project that includes them), so the precedence chain from
the previous section still applies. Tests then layer additional sources
on top of it:

### Layers added by tests (low → high, on top of the layers above)

| # | Layer | Location | Purpose |
|---|---|---|---|
| T1 | Scenario `provisioner.inventory.group_vars` | `tests/molecule/<role>/molecule/<scenario>/molecule.yml` | Per-scenario overrides of any group's vars. Sits at the same precedence as `group_vars/<group>.yml` but wins because Ansible merges scenario inventory last. |
| T2 | Scenario `provisioner.inventory.host_vars` | same file | Per-host identity for the scenario's containers (`postgres_role`, `etcd_seq`). Equivalent to inventory host vars. |
| T3 | Play `vars:` in prepare / converge / verify | `prepare.yml`, `converge.yml`, `verify.yml` | Play-scoped overrides for that play only (e.g. `network_any_address: 0.0.0.0`, `node_sysctl_apply: false`). |
| T4 | `set_fact` in `pre_tasks` | same files | Host-scoped facts that override everything except other `set_fact`. Used to pin runtime-only values that can't be known until the container is up. |

### What scenarios put where, and why

**Scenario `group_vars.all`** — minimum identity needed to make the roles
template correctly:

```yaml
provisioner:
  inventory:
    group_vars:
      all:
        cluster_name: pigsty-lite-test
        cluster_domain: test.local
        pigsty_pki_dir: /etc/pki/pigsty
        postgres_version: 18
        postgres_port: 5432
```

These mirror the contracts in `group_vars/all/main.yml` but with test-safe
values (cluster name doesn't collide with anything, domain is `test.local`).
Set them per scenario rather than relying on the repo-root file so a
scenario stays runnable when invoked from outside the project root.

**Scenario `host_vars`** — only true identity, never config. Container
hostnames map to `postgres_role`, `etcd_seq`, and `postgres_seq`:

```yaml
host_vars:
  pigsty-lite-patroni-ha-1:
    postgres_role: primary
    etcd_seq: 1
```

**Play `vars`** — values that must hold for one play but should not leak
to others. Common pins:

- `network_any_address: 0.0.0.0` / `network_loopback_address: 127.0.0.1`
  — make the bind defaults explicit for the molecule environment.
- `firewalld_default_zone: public` — containers may not have a usable
  firewalld zone definition.
- `node_sysctl_apply: false` — containers can't apply sysctl tuning.
- `repos_pgdg_enabled: true` plus the EL10 repo URL — points the repos
  role at the PGDG RPM instead of the operator-supplied URL.

**`set_fact` in `pre_tasks`** — the test-only escape hatch for values
that depend on container runtime state:

```yaml
pre_tasks:
  - name: Pin advertise addresses to container IP
    ansible.builtin.set_fact:
      etcd_advertise_address: "{{ ansible_facts['default_ipv4']['address'] }}"
      patroni_advertise_address: "{{ ansible_facts['default_ipv4']['address'] }}"
      postgres_listen_address: "{{ ansible_facts['default_ipv4']['address'] }}"
```

This pattern exists because under molecule + podman, `ansible_host` is
the **container name** (e.g. `pigsty-lite-backup-ha-1`), not an IP. Any
variable that defaults to `ansible_host` for its IP (advertise addresses,
listen addresses) renders garbage unless explicitly pinned to
`ansible_facts['default_ipv4']['address']`. In production, `ansible_host`
is a real IP and no such pin is needed.

`set_fact` runs per-host and wins over every other layer, which is exactly
what's needed here — but it also means a forgotten pin in one play and
not another can silently diverge between scenarios. If you add a new
pin, add it everywhere the role runs in that scenario (prepare *and*
converge, both plays if the scenario splits postgres-group hosts from
others).

### What tests deliberately do **not** do

- Tests don't generate or load `group_vars/response.yml`. The configure
  pipeline is exercised by `tests/configure/` (pytest), not molecule.
- Tests don't read `vault_*` overrides. Dev fallback values from
  `group_vars/postgres.yml` are used as-is — that's why those fallbacks
  are obvious `change-me` strings.
- Tests don't use `--extra-vars`. Anything that needs to vary between
  scenarios goes into `molecule.yml` so it's discoverable.

### Adding a new test variable — decision flow

1. **Static value the scenario always needs?** → `provisioner.inventory.group_vars`
   in `molecule.yml`.
2. **Per-container identity?** → `provisioner.inventory.host_vars` in
   `molecule.yml`.
3. **Only relevant to one play (e.g. disable a step for containers)?**
   → that play's `vars:` block.
4. **Depends on runtime container state (IP, hostname, mount)?**
   → `set_fact` in `pre_tasks`. Mirror it in every play that runs roles
   needing the value.

## Reading reality

When debugging variable resolution, prefer `ansible-inventory --host <name>`
and `ansible <name> -m debug -a "var=<name>"` over reading files. The
precedence chain is non-obvious once response.yml and molecule
`set_fact` enter the picture.
